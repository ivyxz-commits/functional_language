# Отчёт о разработке компилятора

## 1. Архитектура

Pipeline из четырёх независимых фаз:

**Исходный код -> Лексер -> Парсер -> Семантика -> Кодоген -> .asm**

Каждая фаза реализована отдельным модулем. Смешивание фаз не допускается.

- **Лексер** - преобразует исходный текст в поток токенов
- **Парсер** - строит AST методом рекурсивного спуска. AST представлен через `std::variant`
- **Семантика** - проверяет типы, разрешает имена, заполняет таблицу типов
- **Кодоген** - обходит AST и генерирует x86-64 NASM ассемблер

---

## 2. Проектные решения

**Метод разбора:** рекурсивный спуск.

**Кодогенерация:** нативный x86-64 NASM, соглашение System V ABI.

**Система типов:** статическая. Типы определяются на этапе компиляции, 
таблица типов передаётся из семантики в кодоген.

**Память:** выделяется через `mmap`, освобождение не реализовано.

**Размер стека:** определяется двухпроходным методом — тело функции генерируется во временный буфер,
после чего вычисляется точный размер фрейма и вставляется `sub rsp`.

**Замыкания:** реализованы как пара `{указатель на код, указатель на окружение}`. 
Окружение выделяется в куче и содержит захваченные переменные.

**Списки вместо массивов:** язык функциональный — вместо массивов используются иммутабельные связные списки. 
Доступ к элементам через pattern matching и рекурсию.

**Циклы не поддерживаются:** вместо них рекурсия.

---

## 3. Ограничения

- Освобождение памяти не реализовано (допускается по тз)
- Cons-выражение `x : xs` только в паттернах
- `map`, `filter`, `foldl` не встроены — реализуются пользователем
- Частичное применение пока не поддерживается
- `GenericType` не поддерживается

---

## 4. Сборка и запуск

### Требования
- `g++` с поддержкой C++23
- `cmake` 3.20+
- `nasm`
- `gcc`

### Сборка
```bash
cmake -B build && cmake --build build
```
возможна быстрая запись без ручного копирования:
```bash
cp examples/partial_apply.lang test.txt && 
cmake --build build --target run
```

Собирается компилятор `lang` и `runtime_functions.o` — объектный файл со встроенными функциями
времени выполнения (`print_float`, `parse_int`, `parse_float`, `str_eq`).

### Запуск программы
```bash
# скопировать пример в test.txt и запустить
cp examples/palindrome.lang test.txt
cmake --build build --target run
```

### Отладка
```bash
# вывод потока токенов
cmake --build build --target dump-tokens

# вывод AST
cmake --build build --target dump-ast

# сборка с отладочными символами (для gdb)
cmake -B build -DCMAKE_BUILD_TYPE=Debug && cmake --build build
gdb ./build/output/program
```

### Запуск программы
```bash
./build/lang program.lang
nasm -f elf64 output/output.asm -o output/output.o
gcc output/output.o build/runtime_functions.o -o output/program -nostartfiles -no-pie
./output/program
```

### Флаги компилятора
```bash
./build/lang --dump-tokens program.lang  # вывод потока токенов
./build/lang --dump-ast program.lang     # вывод AST
```

## 5. Дополнительные возможности

- **ADT** - алгебраические типы данных, включая параметризованные 
  (`data Option[a] = None | Some(a)`). Объявление и pattern matching 
  поддерживаются; полная инстанциация параметров типов не реализована.

- **Pattern matching** - сопоставление с образцом для ADT, списков, кортежей, литералов, wildcard, cons-паттерн `x : xs`

- **Лямбды** - анонимные функции с явной аннотацией типов параметров

- **Замыкания** - лямбды захватывают переменные внешнего окружения

- **Псевдонимы типов** - `type Name = string`

- **Пространства имён** - `module Math { fn add(...) }` с доступом через `Math.add`

- **Кортежи** - `(int64, bool)` с доступом через поля

- **Списки** - иммутабельные связные списки с pattern matching

- **Рекурсия** - функции могут вызывать себя, имя функции доступно в теле

- **Float64** - вещественные числа через XMM регистры и SSE2 инструкции

- **Семантический анализ** - полная проверка типов, разрешение имён, shadowing 


## 6. Реализованные дополнительные пункты

**A.1.7 — Неявное приведение типов**
int64 автоматически приводится к float64 в арифметических операциях,
сравнениях, ветках if и при передаче аргументов в функцию.
Обратное приведение не допускается.

**A.2.1 — Expression-oriented синтаксис**
Язык полностью expression-oriented — все конструкции являются выражениями
и возвращают значение: if/then/else, match, let-in, лямбды, тело функции.
Оператора return нет — результат функции это значение тела выражения.
Помеченные блоки (labeled blocks) не реализованы как избыточные —
их роль выполняет match и вложенные if/else.

**A.2.2 — Алгебраические типы данных (частично)**
Реализованы: объявление ADT через data, конструкторы с полями,
pattern matching для ADT, списков, кортежей, литералов, wildcard,
cons-паттерн x : xs, именованные поля конструкторов.
Option и Result реализуются пользователем через data.
Не реализованы: guards в ветках match, проверка исчерпываемости (exhaustiveness).

**A.2.8 — Функции как значения и лямбда-выражения**
Функции являются значениями первого класса — передаются как аргументы,
возвращаются из функций, связываются с именами через let.
Лямбды с явной аннотацией типов параметров: `\x: int64 -> x + 1`.
Расширяется через A.3.2 — замыкания и частичное применение.

**A.2.9 — Перегрузка функций**
Несколько функций с одним именем и разными типами параметров.
При вызове выбирается версия по точному совпадению типов аргументов.

**A.2.17 — Обобщённые типы (дженерики)**
Функции с параметрами типа: `fn identity[T](x: T) -> T = x`.
Реализованы через мономорфизацию — для каждого конкретного типа
генерируется отдельная версия функции.

**A.3.2 — Замыкания и частичное применение** *(расширяет A.2.8)*
Лямбды захватывают переменные внешнего контекста по значению в момент создания.
Окружение хранится в куче как пара {код, env_ptr}.
Частичное применение: `add(1)` возвращает функцию ожидающую второй аргумент,
реализовано через лямбда-обёртку с захваченными аргументами.

**A.3.4 — Автовывод типов-аргументов**
Параметры типов дженерик-функций выводятся из типов фактических аргументов
через унификацию. Взаимодействует с неявными приведениями.
